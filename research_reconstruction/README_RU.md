# research_reconstruction — гибридная программа Xbox PDB ↔ PC (v0.6.3, дополнено в v0.6.4–v0.6.5)

По ТЗ Андрея и Астры «гибридная программа Xbox PDB ↔ PC Reconstruction». Идея Андрея: Xbox PDB — постоянный
источник имён, раскладок и прототипов. Что подтверждено кодом PC, переносится без повторной реконструкции. Свой
реверс-инжиниринг — только для тупиков, и его выводы снова сверяются с Xbox.

**Опубликованные PDB в этой фазе не менялись** (ТЗ 5: изменение PDB — отдельный этап после приёмки доказательств).
Всё ниже — доказательства, кандидаты на перенос и инструменты. Ни одна реконструкция не выдаётся за исходный код
Bethesda/Obsidian.

## Перепись размеров (v0.6.4, переделана в v0.6.5 по аудиту Астры; Research)

`tools/size_census.py`. **Главное изменение v0.6.5:** перепись выдаёт **наблюдаемый размер выделения**
(`observed_allocation_size`), связанный с классом, а не точный C++ `sizeof`. Блок может быть больше `sizeof(T)`:
хвост, запас, placement new в больший блок. Точный размер — отдельный признак `sizeof_status`.

Два независимых источника, оба — константы компилятора в PC exe:

1. **Выделение → конструктор** (как в v0.6.4).
   - `push imm32` перед вызовом аллокатора: `ourMalloc` 0x00401000, `NiNew` 0x00AA13E0, `MemoryManager::Allocate`
     0x00AA3E40.
   - Блок уходит в функцию как `this` (стенд Unicorn).
   - Класс — по последней записи vtable по `[this+0]`. **Новое:** запись обязана стоять на всех путях от входа
     (граф потока управления, рекурсивный разбор). Ветка «объект не создан» после сравнения блока с нулём не
     учитывается.
2. **Шаг массива (новое).** Вызовы `eh vector constructor iterator` (0x00401050, 0x00EC782F) с постоянными «размер
   элемента» и «конструктор». Шаг массива в C++ — ровно `sizeof(T)`. Контракт итераторов проверяется исполнением до
   переписи: конструктор получает база, база+размер, база+2·размер.

`sizeof_status`:

| статус | когда | классов |
|---|---|---|
| `verified` | sizeof подтверждён в пакете (строгий PDB); выделение и шаг массива ему не противоречат | 23 |
| `supported` | размер выделения (одно значение) = шаг массива (одно значение): два независимых признака | 7 |
| `candidate` | остальное: только выделение (1036), только шаг массива (14). Значение sizeof не выдаётся | 1050 |

Происхождение `sizeof` (`sizeof_origin`) устанавливается только для `supported` / `verified` (15 `xbox-verified`, 15
`pc-reconstructed`). Для `candidate` оно `unknown`. Сравнение размера выделения с Xbox — наблюдение
(`extent_vs_xbox`): равно — 822, отличается — 87, класса нет в Xbox — 102, шаблоны — 54.

| | |
|---|---|
| мест вызова аллокаторов | 5991; размер — константа: 5056; класс назначен: 2768 |
| из них запись vtable на всех путях | все 2768 (отказов path-dependent 0 на настоящем коде; на порченом — отказ, тест) |
| мест вызова итераторов массива | 590; аргументы-константы: 513; класс назначен: 37 (22 класса) |
| классов | 1080: с размером выделения 1065 (одно место выделения — 539), с шагом массива 22 |
| расхождений с sizeof пакета | 0 из 23 |
| нарушений «sizeof наследника ≥ sizeof базы» | 0 (для размеров выделения — только наблюдение: 0) |

Повторные места выделения одного класса **не считаются** независимыми признаками: их число — в колонках
`alloc_sites` / `alloc_callers`.

**В строгий PDB перепись не идёт** (решение Астры по v0.6.4: не массово и не сейчас).

## Новые правила (предлагаются Астре)## Новые правила (предлагаются Астре)

1. **Имя по семейству (маршрут A).** Слот k вводящего класса B. Семейство — все классы exe, у которых B — база на
   смещении 0 (RTTI, без виртуального наследования). Если реализация из семейства стоит во всех vtable exe только в
   слоте k (не ICF) и её имя PC совпадает с именем Xbox для слота k, то слот k = этот метод у всех классов семейства.
   Это то же основание, что статус `name`, найденное у другого переопределения.
2. **Очистка по семейству.** У всех реализаций слота одна очистка (thiscall/cdecl задаются списком параметров,
   переопределение его не меняет). Две разные определённые очистки = противоречие (`conflicted`), а не голосование.
3. **Тождество по поведению R1–R6** — `cases/B01-B08_behavior_pairs/pseudocode.md`.
4. **Опора `end:<A>`** даёт только положение (инвариант в тестах: у 99 таких слотов identity = position).

## Повторить

```
python3 tools/make_syms.py <PDB xNVSE> syms.tsv          # в корне пакета
bash research_reconstruction/run_all.sh <FalloutNV.exe> syms.tsv
```
Нужны Python 3.10+, capstone, pefile, **unicorn 2.1** (`pip install unicorn==2.1.1`). Для пересборки зонда —
clang/lld-link 18 (`runtime_probe/build.sh`). Результат — побайтно те же файлы (`audit/repro_build.log`).

## Ограничения

- Стенд — эмулятор: Unicorn 2.1 не превращает сигнальный NaN в тихий при `fld m32` (Intel SDM требует) — для таких
  входов он не эталон (`cases/A11_copy_to_members/evidence.json`, `x87_snan_probe`).
- Внешние вызовы в прогонах — модели теста; что делает настоящая функция, этим не проверяется.
- Перепись записей полей и поиск вызывающих — в объявленной области, не во всей программе (`limitations.md` случаев).
- Зонд проверен только в эмуляторе. Наблюдения в игре — внешние данные; до трасс пользователя успех не заявляется.
- Имена PC — символы xNVSE (подсказки сообщества). Правила 1 и 3 опираются на них так же, как статус `name`.
- Перепись размеров видит только прямые вызовы трёх аллокаторов и двух итераторов массива с постоянными
  аргументами. Объекты на стеке, внутри других объектов, через другие аллокаторы ей не видны. Класс, который нигде
  так не создаётся, размера не получает. Имя класса шаблона — сырое имя RTTI (`.?AV…`), сверка с Xbox для них не
  делалась.
- Условие «запись vtable на всех путях» — достаточное, а не необходимое. Вызов считается возвращающимся. Ветка
  «объект не создан» определяется по сравнению блока (или его копии) с нулём; ноль в регистре распознаётся по
  `xor r,r` / `mov r,0` линейно от входа вызывающей функции.
- Шаг массива и размер выделения у одного класса обычно связаны одним и тем же конструктором. Независимы значения
  размера (два разных `push` компилятора), а не привязка к классу.
