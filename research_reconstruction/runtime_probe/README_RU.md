# fnv_probe — пассивный зонд для Windows (НЕ запускать до согласования)

Зачем: закрыть вопросы S01/S04 — какой объект на самом деле лежит в поле, через которое делают переход
`NiAVObject::PostAttachUpdate` (поле +0x18) и `NiGeometry::CalculateNormals` (поле +0xB8). Статически доказать это
до конца не удалось (см. `cases/S01-S04_indirect_tail/`).

## Что делает и чего не делает

- На входе в две функции записывает в `Data\NVSE\Plugins\fnv_probe.log` класс объекта в поле (по RTTI), адрес
  vtable и куда ведёт переход. Каждая новая пара — одна строка; повторы только считаются.
- Не меняет данные игры, не вызывает её функций, не трогает аргументы и результат. Читает только то, что
  оригинальный код читает в следующих двух командах, и RTTI в пределах exe.
- **Выключен по умолчанию**: перехваты ставятся, только если рядом лежит файл `fnv_probe_enable.txt`.
- Перед перехватом сверяет байты функции с ожидаемыми (FalloutNV.exe 1.4.0.525 GOG). Не совпали — не ставит.

## Как запустить (когда договоримся)

1. Сделай копию папки игры или хотя бы сохранений. Играть на копии сохранения.
2. Положи `fnv_probe.dll` в `Data\NVSE\Plugins\`.
3. Там же создай пустой файл `fnv_probe_enable.txt`.
4. Запусти игру через xNVSE, загрузи копию сохранения, походи 2–3 минуты (смена локации, бой, NPC рядом).
5. Выйди из игры. Пришли `Data\NVSE\Plugins\fnv_probe.log`.
6. Удали `fnv_probe_enable.txt` (или саму DLL).

## Проверено

Только в эмуляторе (`out/probe_selftest.json`, 15 из 15): без файла-флага байты exe не меняются; с флагом ставятся
ровно два перехвата; регистры, флаги и стек на входе в цель перехода — те же, что без зонда; в журнале — имя класса и
цель; при других байтах exe перехват не ставится. Потоки игры, загрузчик xNVSE и реальная память игры там не
моделируются — это проверит только запуск на Windows.

Разбор журнала: `python3 -I -B parse_log.py <FalloutNV.exe> <syms.tsv> ../out/rtti_census.json fnv_probe.log out.json`.
