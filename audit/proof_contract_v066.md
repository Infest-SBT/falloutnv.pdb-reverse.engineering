## 1. P1-A: `ret N` — по графу потока управления

Новый общий модуль `tools/allocchain.py` делает разбор по графу: capstone и образ exe.

`terminal_rets(f, end)`:
- проходит все пути от входа после цепочки `jmp`: обе ветви `jcc`, цель `jmp`; `call` считается возвращающимся;
- граница функции — следующий символ xNVSE;
- собирает **все достижимые** `ret`.

Доказательство `ret-n` есть, только если все достижимые `ret` дают одно N. В записи перечислены все эти `ret`
(`rets`). Не доказано, если встречается:
- косвенный переход (таблица ветвлений);
- выход за границу функции (хвостовой переход в соседнюю);
- `int3` или неразбираемый байт.

Тогда остаётся только журнал `cleanup-journal`, и причина записана в `ret_cfg`.

Итог:
- 455 уникальных функций доказаны по графу;
- у 27 утверждений очистки — только журнал: таблицы ветвлений и 3 выхода в соседнюю функцию;
- расхождений между графом и прежним журналом нет.

Контрпример Астры (недостижимый `ret 4`, на реальных путях `ret 8`) в `tools/test_cfg_proofs.py` воспроизведён
настоящими байтами x86: доказательство `ret 4` невозможно, граф даёт {8}. Там же:
- несовместимые `ret 4`/`ret 8` на разных путях;
- хвостовой переход в соседнюю функцию;
- косвенный переход.

## 2. P1-B: «выделение → указатель → this → vptr»

`allocchain.alloc_chain`:
1. `push N` сразу перед вызовом аллокатора (ourMalloc / NiNew / MemoryManager::Allocate);
2. от команды после вызова — **must-alias указателя** по графу вызывающей. Где на ВСЕХ путях лежит блок: регистр или
   `[ebp±d]`, пересечение на слиянии, `call` стирает eax/ecx/edx. Ветка «объект не создан» (je/jz после сравнения
   блока с нулём) не учитывается;
3. дальше одно из трёх:
   - встроенная запись `mov [x], vt`, где x — блок, на всех путях;
   - вызов конструктора с `ecx` = блок на всех путях, а в конструкторе — запись `vt` по **this** (must-alias от `ecx` на
     входе) на всех путях от входа;
   - у класса нет vtable: первый вызов с `ecx` = блок — метод класса по символу xNVSE. Это `assumption` в записи.

Отвергается:
- `ecx` не из блока;
- `lea ecx, [eax+4]` (подобъект или смещённый указатель);
- запись `vt` в чужой объект (`mov [ebx], vt` — контрпример Астры);
- запись `vt` не на всех путях;
- vtable другого класса.

Все случаи — в `test_cfg_proofs.py`.

**`ctor-alloc` теперь доказывает только верхнюю границу** (`bound: upper`, sizeof ≤ N) и в контракт точного `sizeof`
не входит. Точный размер дают:
- `subclass-boundary`;
- `alloc-bounds` — цепочка + нижняя граница = N;
- `manual-reviewed`.

Нижняя граница — **без допущения о выравнивании**. Это наибольший конец:
- подтверждённого поля класса или его баз;
- подтверждённого обращения метода самого класса по `this`.

Итог:
- 62 доказательства `ctor-alloc`: 39 — через запись vtable по this, 23 — через метод класса без vtable (допущение);
- 9 строк журнала цепочку не прошли, причины записаны в `unlinked_allocations`;
- точная граница sizeof: 69 классов; только верхняя: 13 классов; нет границы: 2 класса (`TESForm` — внешнее основание
  xNVSE, `NiAlphaAccumulator` — удержан);
- **14 утверждений `sizeof` получили происхождение `unknown`**: 13 только по верхней границе и `NiAlphaAccumulator`.
  Статус размера в строгом PDB у них прежний: Астра сказала, что ранее подтверждённые размеры сохраняются, но им нужен
  отдельный независимый основания;
- **список на пересмотр:** `MemoryHeap`, `BGSSaveLoadGame`, `BGSSaveLoadManager`, `FalloutRadio::FORadioStation`,
  `RadioConvTask`, `Font`, `FontManager`, `BSFadeNode`, `NiPropertyState`, `BSShaderAccumulator`, `NiDX9Renderer`,
  `ShadowSceneNode`, `ShadowSceneLight`. Для них нужен второй признак.

## 3. P1-C: `field-access` — ширина, направление и база из самой команды

У каждой записи есть `operand_size` и `access` (`read` / `write` / `read-modify-write` / `address`), вычисленные
capstone из команды. `lea` и `add reg, imm` — вычисление адреса, не чтение. Проверка `check()` пересчитывает это и
сверяет с записью и с журналом **независимо друг от друга**:
- для чтения и записи журнал обязан совпасть с командой по ширине и `write`;
- для «адреса» ширина и запись в журнале — результат трассировки (адрес передан дальше, например в
  `InterlockedIncrement`). Это записывается как `assumption`, и такое обращение не идёт в контракт ширины.

Контракт ширины (основание `access-width`): нужна команда, читающая или пишущая операнд именно этой ширины.

База обращения: для `this` (`class-method-this` / `subclass-method-this`) — must-alias от `ecx` на входе функции по
графу. Это записано в `base_chain`; если не прослежена — `assumption`.

Итог:
- read 2004, write 1486, address 389, read-modify-write 13;
- база прослежена у 3544 обращений, не прослежена у 22 (допущение журнала), у остальных база — не this (глобальный
  объект, аргумент…);
- расхождений журнала с командой по ширине и направлению — 0.

Тест «совместная подмена журнала и доказательства при тех же байтах exe»: 4-байтное обращение объявлено 2-байтным и
в журнале, и в записи — отказ. Ширину даёт команда, а не журнал.

## 5. Правило `evidence.py` (решение Астры «ДА, ОБЯЗАТЕЛЬНО»)

- «Граница наследника» принимается только по **подтверждённому** первому собственному полю наследника (для
  вложенного объекта — по его члену на смещении 0). Четыре строки журнала стали `subclass-boundary-unconfirmed`
  (accepted False): `NiNode`, `NiRefObject`, `BSShaderLightingProperty`, `NiAlphaAccumulator`.
- Новое основание **`alloc-bounds`** — цепочка `allocchain` плюс нижняя граница без выравнивания. Принято у 24 классов,
  все уже были подтверждены, **повышений нет**: правило записывает alloc-bounds кандидатом, если статус был ниже.
- Итог по основаниям: `size_basis` изменился у 25 классов, `size_status` — ни у одного:
  - `BSShaderLightingProperty`: subclass-boundary → **alloc-bounds**. `NiNew(0x7C)` в `CreateClone` → встроенная запись
    vtable 0x00B7184A; поле `kLightListFence` +0x78..0x7C;
  - у 23 классов alloc-bounds добавился вторым основанием;
  - **`NiAlphaAccumulator` удержан**: `size_basis = held-pending-audit`, причина — в `evidence_spec.json →
    size_status_hold`. Доказано 0x33 ≤ sizeof ≤ 0x34; 0x34 — только по выравниванию.
- Полное понижение убрало бы из строгого PDB `NiAlphaAccumulator` и наследника `BSShaderAccumulator`. Готовый
  вариант — `audit/strict_candidate_without_hold/`: PDB, заголовок, diff, как собрать. Решение — за Астрой.
