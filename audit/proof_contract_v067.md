# v0.6.7: ответ на аудит Астры v0.6.6 — P0 (14 размеров), P1 (частичные регистры, граница команды), P2

Аудит v0.6.6 (31.10.2026) дал условный допуск ко второй исследовательской части. Перед любым переносом в Strict он
потребовал мини-этап P0/P1. Этот файл описывает:
- что сделано по каждому пункту;
- что изменилось в доказательствах, статусах и строгом PDB;
- что модель по-прежнему допускает.

Машинные сравнения генерируются при сборке:
- `audit/diff_v066_v067.md` — пакет;
- `audit/proofs_diff_v066_v067.md` — доказательства;
- `audit/sizeof_evidence_reaudit.csv` — 14 размеров;
- `audit/strict_header_raw_v066_v067.diff` — строгий заголовок.

**Итог одной строкой:**
- 9 классов честно понижены и ушли из строгого PDB;
- 5 из 14 (и ещё 24 класса) получили второй, независимый признак точного размера — удаляющий деструктор;
- research PDB побайтно тот же;
- поля и слоты не изменились ни у одного класса.

## 1. P1: частичные регистры (контрпример Астры)

`tools/allocchain.py`, перенос состояния `_transfer`:
- **Запись в частичный регистр стирает полный.** Это касается `al/ah/ax → eax`, и так же для `ebx/ecx/edx`, `si/di/bp/sp`
  и `sil/dil/bpl/spl`. Покрыты `mov`, `movzx`, `setcc`, `xor al, al`, неявные записи (`lodsb`, `cbw`, `cdq`, `xchg`, `mul`…
  через `regs_access` capstone) и запасное правило «первый операнд-регистр записывается» для команд не из списка
  чтения.
- **Частичный регистр не бывает местом указателя.** Указатель лежит только в 32-битном регистре или в 4-байтной
  ячейке `[ebp±d]`.
- **`mov al, 0` не делает `eax` нулём.** Нуль бывает только у полного 32-битного регистра.
- **Если capstone не смог перечислить записи команды — закрытый отказ:** стирается всё.

Репро Астры на настоящих байтах `89 C8 B0 00 C7 00 78 56 34 12 C3` даёт: записи vptr нет. В `tools/test_cfg_proofs.py`
к нему добавлены `movzx eax, al`, `sete al`, `mov ax, 0`, `mov ah, 1`, `xor al, al`, `lodsb`, `cbw`, `xchg eax, edx`,
`mov cl, 0` (частичная запись в сам this) и контрольный случай, где alias сохраняется. Скрипт Астры
`FNV_v066_partial_register_boundary_counterexamples.py` на новом коде падает на своём `assert 'Bug no longer reproduces'`,
то есть ошибка больше не воспроизводится. Копия скрипта с обращёнными `assert` проходит; лог — в архиве проверок.

## 2. P1: команда, заходящая за конец функции; переходники

- Во **всех** обходах (`terminal_rets`, `reaches_all`, поток данных `_flow`/`alias_at`, `vptr_writes`, `sized_delete`)
  требуется `адрес + длина ≤ конец функции`. Если команда заходит за конец, это отказ с причиной. В `reaches_all` такой
  путь не считается дошедшим.
- Репро Астры: `ret 4` на `0x40100F` при конце `0x401010` даёт «не доказано» с причиной «команда заходит за границу».
  В тест добавлены также запись vptr за концом, `alias_at` с причиной отказа и `ret 8` за концом на одном из путей.
- **`entry_of` больше не прыгает куда угодно.** `jmp` в начале функции считается переходником, только если его цель —
  начало другой функции по символам xNVSE. Это `Img.starts`, функция `thunk_chain`. Иначе вход — сама функция: обход
  идёт по `jmp`, и выход за область — отказ. Подтверждённый переходник записывается в доказательство `ret-n`: поле
  `thunks` и допущение.

## 3. P2: must-zero по графу; модель кадра; допущения в каждом доказательстве

**`zero_regs` → по графу.** Нули для «`cmp eax, ebx` при `ebx = 0`» берутся из потока данных от входа вызывающей
функции до команды после аллокатора. Это пересечение по всем путям, `state_at`. Тесты:
- обнуление только в недостижимом блоке — сравнения с нулём нет, цепочка не доказана;
- обнуление на одном пути — не доказана;
- `xor ebx, ebx; mov bl, 1` — не доказана;
- контроль: обнуление на всех путях — доказана.

**Модель кадра стала строже.** Проверяя исправление, я нашёл у ячеек `[ebp±d]` ещё три дыры той же природы, что
частичный регистр:
1. ячейка считалась ячейкой кадра, даже когда `ebp` — обычный регистр (в оптимизированном коде `ebp` часто = this);
2. запись через другой указатель могла попасть в ячейку;
3. байтовая запись в часть ячейки её не стирала.

Теперь:
- **Ячейки `[ebp±d]` существуют, только пока `ebp` — указатель кадра этой функции на всех путях.** Это после `mov ebp,
  esp` и до любой записи в `ebp`. Запись в `ebp` стирает все ячейки, а `ebp` как обычный регистр остаётся местом
  указателя.
- **Запись в `[ebp+d]` стирает все перекрытые ячейки**, по байтам.
- **Утечка адреса кадра отслеживается.** Она возникает при `lea r, [ebp+X]`, при `lea r, [esp+X]` и при копии
  `ebp`/`esp` в регистр, память или стек. После неё `call` и запись через неотслеживаемый указатель стирают ячейки от
  утёкшего адреса вверх. Утечка `esp` — это утечка всего кадра.
- **Записи без утечки.** Запись через сам отслеживаемый указатель (this с входа или новый блок из аллокатора) и запись
  по абсолютному адресу кадр этой функции не задевают.
- Тесты: 12 новых случаев на настоящих байтах — утечка внизу, внутри и выше ячейки, утечка `esp`, копия `ebp`,
  `mov ebp, esi`, `xor ebp, eax`, cookie `/GS` и контрольные случаи.

**Допущения записываются в каждое применённое доказательство** (`cfg_assumptions`): `ret-n`, `ctor-alloc`,
`alloc-bounds`, `sized-delete` и `field-access` с прослеженной базой. Проверка `check()` пересчитывает запись целиком,
поэтому запись без допущений отвергается. Тест порчи: убранные `cfg_assumptions` дают отказ. Допущения:
- `call` возвращается: невозвращающиеся вызовы и исключения не моделируются;
- граница функции — следующий символ xNVSE;
- `push`/`call` пишут ниже `esp`, а не в живые ячейки кадра;
- адрес кадра попадает в чужой код только через `ebp`/`esp` этой функции; по `[ebp+X]` доступны адреса не ниже X;
- `xor r, ebp/esp` — только шифрование cookie `/GS` (иначе каждая функция с `/GS` теряла бы кадр);
- для `sized-delete` ещё два — см. раздел 5.

**`ret-n` доказывает только очистку стека.** В каждой записи есть поле `proves`: «только очистку стека N байт при
выходе; соглашение о вызове, число и типы параметров не доказывает». В контракте `ret-n` стоит только у
`vslots.stack_cleanup`. Тест порчи: запись, выдающая себя за доказательство соглашения о вызове, отвергается.

## 5. P0: 14 размеров — `audit/sizeof_evidence_reaudit.csv`

**Правило `evidence.py`.** Строки `ctor-alloc` и `ctor-alloc-derived` больше не принимаются как точный размер:
`accepted False`, в строке записана причина. Выделение наследника даёт ту же верхнюю границу (sizeof ≤ sizeof
наследника ≤ N). Удержание удалено: `size_status_hold` в `evidence_spec.json` запрещён `assert`-ом, и `held-pending-audit`
больше нигде не встречается. Если принятого основания не осталось, статус падает. Появляется строка `bounds-only` с
машинными нижней и верхней границей.

**Новый независимый признак — удаляющий деструктор (`sized-delete`).** У классов Gamebryo функция слота 0 первичной
vtable — удаляющий деструктор. На пути освобождения стоит:

```
push N            ; размер
push this         ; must-alias от ecx на входе
call NiDelete     ; NiDelete(p, n) → NiMemManager::Deallocate(p, 3, n)
```

Правило C++ для классового `operator delete(void*, size_t)`: передаётся размер удаляемого объекта. Удаляющий
деструктор класса T передаёт `sizeof(T)`, и это **точный** размер. Он не зависит от выделения: другая функция и другое
правило языка. Выравнивание тут ни при чём: при `#pragma pack(1)` (контрпример Астры) компилятор передал бы 0x33.
Доказательство принимается, только если выполнено всё:
1. vtable принадлежит классу — по RTTI (COL со смещением 0 → TypeDescriptor → имя) или по единственному символу xNVSE
   `??_7` (RTTI нет);
2. в функции слота 0 на пути подряд стоят `push N; push R; call NiDelete`, где R — this (must-alias);
3. функция связана с классом — пишет vtable класса по this на всех путях или вызывает (ecx = this на всех путях)
   деструктор, который пишет её по this на всех путях своего тела. Это закрывает унаследованный удаляющий деструктор
   базы и ICF;
4. освобождение достижимо только через эту связь;
5. все размеры освобождения в функции одинаковы.

Сверка по всем 52 классам с vtable: признак есть у 29, **у всех 29 размер совпал с `pc_size`**, расхождений 0. Это
независимая перекрёстная проверка всей таблицы размеров. У остальных 23 классов признака нет: глобальное
`ourFree`/`MemoryManager::Deallocate` без размера, или функция слота 0 не связана с классом. Так у `NiTriShape`,
`NiTriStrips`, `NiObject`, `NiShadeProperty` и `NiD3DPass` — это закрытый отказ. Повышений нет: основание принимается,
только если статус уже был `confirmed`. Тесты в `test_cfg_proofs.py`: положительный — через запись vtable и через
деструктор; отрицательные — освобождается не this, нет связи, запись vtable только на пути без освобождения,
«деструктор» пишет в чужой объект, вызов не освобождения с размером, чужая vtable.

- Безопасного ограниченного представления (VerifiedPrefix) для них не делал. По существующей политике оно
  оформляется отдельным решением в spec, а условие 7 (`prefixview`) исключает классы с vtable, базами или массивами.
  Добавлять его сейчас — новое содержимое Strict без независимой проверки.

## 7. Повторить

Как в v0.6.6. `audit/repro_build.log` в чистой копии заново выполняет `evidence.py`, происхождение и реестр и
пересобирает оба PDB из `tools/fnv_types_v05*.cpp` побайтно. `gen_headers.py --strict` требует дамп Xbox PDB, его в
пакете нет. Поэтому строгий заголовок приложен готовым, а сырой diff — в `audit/strict_header_raw_v066_v067.diff`.
